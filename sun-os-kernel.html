Beyond Multiprocessing: Multithreading the SunOS Kernel

A structured guide to Eykholt et al.’s USENIX Summer ’92 paper, expanded from your notes with definitions, diagrams, design reasoning, and likely exam connections.

Big pictureArchitectureScheduling SynchronizationInterrupt threadsLocking Exam reviewGlossary
One-sentence thesis: SunOS 5.0 rebuilt the kernel around fully preemptible kernel threads, allowing asynchronous work, user-level multithreading, interrupts, real-time scheduling, and multiprocessor execution to use one consistent scheduling and synchronization model.

1. The problem and the design answer

Why “just add locks” was not enough

  • Multiprocessors need high concurrency: independent work must run simultaneously on different CPUs.
  • User processes need multiple independent flows that can make system calls and handle page faults.
  • Real-time work needs bounded dispatch latency: a high-priority runnable thread must not wait behind an unbounded critical section.
  • Interrupt handlers traditionally run in a constrained context: they cannot safely sleep or call code that may block.

SunOS response

threads everywherepreemptionpriority inheritance

Make the kernel thread the fundamental schedulable entity. Build system activity and interrupt work from the same primitive, then protect shared data with explicit synchronization objects.

The central architectural move: make all important execution contexts schedulable as threads.

2. The execution model: process, LWP, and kernel thread

The terms are related but not interchangeable. This distinction is a frequent exam target.

Key fact: every LWP has a kernel thread, but not every kernel thread has an LWP. User-level threads can be many-to-many over a process’s LWPs.

Kernel thread

The schedulable entity: small structure, stack, kernel registers, scheduling class, priority, and links to LWP/process/CPU. Switching it does not require changing address-space information.

LWP

Kernel-supported execution context inside a process. It stores user-visible state and is swappable. A user thread library can switch between user threads without entering the kernel.

CPU structure

Per-processor state points to the current thread, idle thread, dispatching information, and interrupt handling state. The current thread gives fast access to related structures.

3. Scheduling and preemption

Dispatcher rule

  1. A scheduling class converts its class-specific priority into a global priority.
  2. The dispatcher chooses the runnable thread with the greatest global priority.
  3. Equal-priority threads run round-robin.
  4. When a high-priority thread becomes runnable, the current thread is preempted as soon as practical, except in a small bounded non-preemptible region.
Priority is contextual: with priority inheritance, a thread’s effective priority reflects both the service it is performing and the higher-priority work it is blocking by holding a lock.

Scheduling classes

  • System: kernel/system activity.
  • Timesharing: ordinary workloads.
  • Real-time: fixed-priority scheduling.

Exam phrase: scheduling operates on threads, not processes.

On an SMP system, another CPU may also be directed to preempt its current lower-priority thread.

4. Synchronization architecture

Mutex

Mutual exclusion: at most one owner enters a protected region. SunOS adaptive mutexes spin while the owner is running, then sleep if the owner stops running.

Condition variable

Wait for a condition while releasing a mutex; another thread signals one waiter or broadcasts to all. Signal-aware variants can return when interrupted.

Readers/writer lock

Many readers may enter together, but a writer is exclusive. Writer ownership supports priority inheritance; read ownership is harder to enumerate.

Semaphore

A counter representing available units of a resource. “P” waits/decrements; “V” signals/increments. It need not have a single owner.

Adaptive mutex decision

locked? → owner running: spin briefly; owner not running: sleep. This avoids an expensive sleep/wakeup when a running owner is about to release the lock.

Priority inversion

Low-priority L holds a lock needed by high-priority H, while medium-priority M runs. Priority inheritance temporarily boosts L so it can finish and release the lock.

Why turnstiles? Synchronization objects stay small, while each turnstile gives a lock its own predictable wait queue. Hashed queues could be shared by unrelated locks, making real-time behavior less predictable.

5. Interrupts as threads

Traditional drawback

  • Interrupt handler may deadlock on a lock held by the interrupted code.
  • Interrupt priority must be raised/lowered around many locks.
  • Handler runs in a restricted context and cannot sleep safely.

SunOS technique: lazy thread conversion

  1. Preallocate partly initialized interrupt threads.
  2. On interrupt, do minimal work and run on that thread’s stack; the interrupted thread is pinned.
  3. If no lock contention occurs, return cheaply.
  4. If the handler blocks, save state (“passivate”) and become a full schedulable thread; the pinned thread can resume.

→

The optimization pays the full thread-conversion cost only when the interrupt actually needs to sleep.

Important nuance: while an interrupt thread is active, its interrupt level and lower levels remain blocked. The configurable “thread level” determines which interrupts can be handled as threads; higher-priority firmware-like interrupts use spin synchronization.

Clock interrupt special case

There is one clock interrupt thread for the whole system, not one per CPU. If another tick arrives while it is active, the handler clears the interrupt and increments a counter; the clock thread processes the missed tick before returning. This is rare and usually indicates heavy higher-level interrupt activity or debugging.

6. Locking, drivers, and implementation tools

Data-based locking

Locks protect shared data, rather than entire routines. The design rule is: every piece of shared data has a synchronization object.

MT-safe vs. MT-unsafe drivers

Unsafe drivers are wrapped by one global unsafe_driver mutex, serializing their entry points, interrupts, and callbacks. Safe drivers provide their own locking; “MT-hot” means fine-grained locking.

Kernel time slicing

The clock handler can preempt kernel threads even on a uniprocessor, creating many interleavings that expose missing locks. It is primarily a debugging feature.

locknest

A lint-like static analyzer that builds call graphs and reports lock-order cycles. It finds hierarchy violations before they become runtime deadlocks.

7. Exam-ready synthesis

Compare the trade-off: threads simplify structure and enable concurrency, preemption, and real-time scheduling—but stacks consume memory and context switches remain expensive. Some tiny activities are still better as callouts or “zero-weight” processes.

Common questions and compact answers

Why separate user-level threads from LWPs?

The library can switch between user threads without entering the kernel, while many user threads can share a smaller number of kernel-supported LWPs and avoid excessive kernel resource use. A thread bound to an LWP can still use a specific kernel execution context.

How does SunOS reduce priority inversion?

Locks with identifiable owners support priority inheritance. A lock holder inherits the priority of blocked higher-priority work, finishes its critical section sooner, and releases the lock.

Why are adaptive mutexes preferable to always spinning?

Spinning is useful when the owner is currently running and will release soon; sleeping is better when the owner is not running. Adaptive behavior combines low latency with lower wasted CPU time.

What is the key difference between a traditional interrupt and a SunOS interrupt?

A traditional handler keeps the interrupted execution captive and avoids sleeping. SunOS treats most interrupts as high-priority asynchronous threads, so they can use normal synchronization and block when necessary.

What deadlocks can the runtime detector miss?

Priority-inheritance-based detection works well for mutexes and write-held readers/writer locks, but cannot always detect reader/writer deadlocks involving read holders because there is no complete list of reader owners. Condition-variable deadlocks are also not detected.

Last-minute checklist

  • Kernel thread = scheduled entity.
  • Every LWP has a kernel thread; converse is false.
  • Dispatcher selects greatest global priority.
  • Ties use round-robin.
  • Preemption is disabled only in bounded regions.
  • Adaptive mutex: spin if owner runs, sleep otherwise.
  • Turnstiles avoid shared hashed wait queues.
  • Interrupts can sleep because they are threads.
  • One clock thread per system.
  • locknest checks lock-order cycles statically.

8. Technical vocabulary

Preemption

Forcibly stopping a running thread so a more urgent runnable thread can use the CPU.

Dispatch latency

Time between a thread becoming runnable and actually receiving CPU time; real-time systems try to bound it.

Critical section

A bounded region accessing shared state that must not interleave unsafely with another thread.

Passivation

Saving an interrupt thread’s state when it blocks so it can later run as a normal schedulable thread.

Priority inversion

A high-priority thread waits indirectly for low-priority work while medium-priority work runs.

Symmetric multiprocessing

An SMP system lets equivalent CPUs run threads from the same kernel and share memory.

Swappable

Eligible to move between memory and secondary storage; LWP data/stacks may be swappable, core thread data is not.

Bounded section

A non-preemptible region whose maximum execution time is limited, preserving real-time guarantees.
